# Subsea Cable Digital Twin & Multi-Sensor Early Warning System

## 1. Primary Objective & Architectural Scope

The **AbyssLink Digital Twin + Multi-Sensor Early Warning Demonstrator** upgrades the SUBSEA research platform into a hybrid physical–digital-twin early warning demonstrator for subsea cable disturbance assessment.

The demonstrator operates in two distinct, verifiable modes:
1. **Physical-Only Mode:** Evaluates disturbance and warning states strictly from verified AbyssLink physical prototype sensors (ESP32 serial telemetry: piezo vibration, HC-SR04 ultrasonic distance, and laser/LDR optical link). Simulated channels are completely isolated and excluded.
2. **Hybrid Demonstration Mode:** Concurrently ingests physical telemetry alongside software-synthesized benchmark channels (DAS-like spectral acoustic RMS, virtual vessel kinematics/proximity, seafloor benthic temperature, and cable mechanical strain). Every channel carries an immutable data provenance tag (`DataSource.PHYSICAL` or `DataSource.SIMULATED`).

> [!IMPORTANT]
> **Scientific Integrity & Simulation Disclaimer:**
> Software channels generated by the digital twin are mathematical benchmark models created for algorithmic demonstrator evaluation under repeatable conditions.
> They are **not** real measurements from seabed DAS equipment, benthic temperature probes, marine AIS tracking systems, or subsea cable infrastructure.
> Synthetic simulation performance does **not** establish real-world subsea damage-detection accuracy.

### Module Responsibilities

1. **`src/subsea/provenance_quality.py`**:
   - `DataSource` (`PHYSICAL`, `SIMULATED`): Enforces immutable provenance.
   - `DataQuality` (`GOOD`, `DEGRADED`, `STALE`, `INVALID`, `MISSING`, `OUT_OF_RANGE`, `CONTRADICTORY`).
   - `SensorReading`: Standardized reading dataclass with metadata audit reasons.
   - `DataQualityValidator`: Validates physiological ranges, monotonic time stamps, staleness (>2.0s), and contradictory sensor states.

2. **`src/subsea/digital_twin.py`**:
   - `DigitalTwinSimulator`: Stateful, deterministic temporal evolution model.
   - `TwinScenario`: Implements all 7 standardized scenarios with deterministic RNG seeds.
   - `DigitalTwinFrame`: Synchronized multi-channel frame payload.

3. **`src/subsea/early_warning.py`**:
   - `EarlyWarningEngine`: Independent warning state machine with hysteresis.
   - States: `W0` (Normal), `W1` (Watch), `W2` (Advisory), `W3` (Urgent), `WX` (Unknown/Data Quality).
   - Multi-sensor corroboration: requires at least two independent sensor groups to escalate to W3.
   - Fail-safe response: trips to WX when sensor channels are missing, stale, invalid, or contradictory.

4. **`scripts/run_abysslink_demo.py`**:
   - Runnable CLI demonstrator operating without physical hardware.
   - ANSI dashboard displaying live warning state, disturbance state, and sensor metrics.

5. **`scripts/evaluate_digital_twin.py`**:
   - Repeatable scenario benchmark evaluation suite. Measures detection latency, false-positive rate, W3 latency, and recovery time.

6. **`web/js/pages/hil.js`**:
   - Full interactive web dashboard supporting both direct Web Serial USB hardware connection and interactive digital twin simulation.

## 3. Digital Twin Scenario Definitions

| Scenario ID | Name | Initial Conditions | Progression & Target Semantics | Expected Warning Transition |
|---|---|---|---|---|
| 1 | `normal_operation` | Vessel at 350m, Speed 6m/s, RMS 0.08, Temp 4.0°C | Safe transit parallel to cable route (>200m away). Ambient baseline conditions. Zero false alarms. | **W0** (Hold) |
| 2 | `approaching_vessel` | Vessel at 80m, Speed 3.5m/s heading toward cable (X=0) | Steady advance toward cable route. Crosses 60m threshold at ~6s, entering corridor. Acoustic RMS rises inversely with distance. | **W0 ➔ W1 ➔ W2 ➔ W3** |
| 3 | `low_level_vibration` | Vessel at 180m, RMS baseline elevated to 0.35 | Low-level acoustic anomaly onset without physical cable strike. Demonstrates sensitivity to subtle anomalies without false W3 escalation. | **W1 ➔ W2** |
| 4 | `increasing_disturbance` | Vessel at 35m, RMS 0.55 ramping to 1.4, Strain ramping to 230με | Escalating mechanical tension and acoustic energy simulating progressive anchor dragging or seafloor scouring. | **W2 ➔ W3** |
| 5 | `severe_disturbance` | Vessel crossing route (X=10m to -10m), RMS 2.4, Strain 380με | Severe cable strike or heavy anchor trawl across route. Multi-sensor corroboration triggers rapid strike warning. | **W2 ➔ W3** (Rapid, <=1.5s) |
| 6 | `sensor_degradation` | Ambient baseline, noise injected, dropout after 10s, stale after 12s | Sensor communication loss or hardware degradation. Fails safe by tripping directly to WX. Never silently masks corrupt data as normal. | **W1 ➔ WX** |
| 7 | `recovery` | Starts at severe disturbance (RMS 1.2, Strain 200με), exponential decay | Disturbance ceases and decays exponentially back to ambient baseline. Demonstrates staged de-escalation with hysteresis. | **W3 ➔ W2 ➔ W1 ➔ W0** |

## 4. Early Warning States & Transition Rules

- **`W0 — Normal`**: No warning criteria met. Ambient background conditions.
- **`W1 — Watch`**: Initial anomaly onset (e.g., vessel enters 60m corridor, or single elevated acoustic band).
- **`W2 — Advisory`**: Persistent anomaly (>= 3 consecutive frames) or at least two corroborating sensor indicators.
- **`W3 — Urgent`**: High-confidence critical disturbance sustained across >= 5 consecutive frames **and** corroborated by at least two independent sensor groups. A single simulated feature alone cannot jump to W3.
- **`WX — Unknown / Data Quality`**: Missing, stale (>2.0s), out-of-bounds, or contradictory sensor readings. Warning decisions are suspended to prevent misleading guidance.

### Decoupling from Disturbance Pipeline ($T0-TX$) & Heuristic Labeling Rule

- The $T0/T1/T2/T3/TX$ classification evaluates immediate physical disturbance signatures using multimodal fusion ($C_P, C_A, R, U$), whereas $W0/W1/W2/W3/WX$ provides advance predictive situational awareness. Both outputs run concurrently and are displayed separately.
- In the digital twin testbed (`/api/twin/step` and `twin_runs.json`), simulated frames provide high-level scalar summaries (RMS, distance, strain) rather than raw 50 Hz triaxial accelerometer time series buffers. Therefore, the twin state is evaluated via benchmark heuristic rules and is explicitly labeled:
  > **`twin_heuristic_state`**: *"Twin heuristic (NOT the fusion classifier)"*
- This ensures full scientific integrity: simulated benchmark metrics are never misrepresented as outputs of the trained empirical fusion classifier.

### Multi-Tab Session Isolation & API Architecture

- **Per-Session State (`TwinSession`)**: Replaced global simulation instances with per-session state in `scripts/serve_web.py`. Each browser tab generates a UUID session ID (`session_id`) passed in JSON body, `X-Session-ID` header, or `?session=` query parameter.
- **Concurrency**: Two browser tabs can run simulations, step, and reset completely independently without crosstalk or interleaved step indices.
- **Lifecycle & TTL**: Inactive sessions expire after 1 hour (TTL). Missing session IDs default to the `"default"` session for backward compatibility.
- **Endpoints**:
  - `POST /api/twin/set_scenario`: Configures scenario, operating mode, and seed. Validates scenario (unknown -> 400).
  - `POST /api/twin/step`: Advances simulation by clamped `dt` (`[0.05, 5.0]`). Returns readings, early warning decision, twin heuristic state, indicator groups, hold progress, ground-truth `t_event`, and config hash.
  - `POST /api/twin/reset`: Resets simulator and early warning engine for the session.
  - `GET /api/twin/export?session=<id>`: Streams recorded run as JSONL in `artifacts/digital_twin/*.jsonl` format.
- **Offline Static Replay**:
  - `web/data/twin_runs.json` contains precomputed seeded runs for all 7 scenarios. If `/api` is unreachable or reports mode `"static"`, the UI falls back automatically to offline replay with a visible `STATIC REPLAY` badge and integrity verification.

## 5. Execution Instructions

### A. Run Offline Terminal Demonstrator (No Hardware Required)

```powershell
# Windows PowerShell
$env:PYTHONPATH='src'

# Run approaching vessel scenario
python scripts/run_abysslink_demo.py --scenario approaching_vessel --duration 15.0

# Run in Physical-Only mode (demonstrating honest isolation)
python scripts/run_abysslink_demo.py --scenario approaching_vessel --mode physical --duration 5.0

# Run severe disturbance scenario with seed
python scripts/run_abysslink_demo.py --scenario severe_disturbance --seed 42
```

### B. Run Scenario Evaluation Benchmark

```powershell
$env:PYTHONPATH='src'
python scripts/evaluate_digital_twin.py
```
Outputs a full summary scorecard to `artifacts/digital_twin/evaluation_report.md`.

### C. Run the Web Dashboard

```powershell
$env:PYTHONPATH='src'
python scripts/serve_web.py --port 8000
```
Then navigate to: **`http://localhost:8000/#/hil`**
- Toggle between **`🌐 Hybrid Digital Twin Mode`** and **`🔒 Physical-Only Mode`**.
- Select any of the 7 scenarios from the dropdown.
- Click **`▶ Run Simulation`** or **`⏭ Step Frame`** to interactively visualize the 2D cable route map and multi-sensor signal traces.
- Connect an optional AbyssLink ESP32 via Web Serial (115200 baud) for live hardware-in-the-loop testing.

### D. Run Automated Test Suite

```powershell
$env:PYTHONPATH='src'
pytest tests/test_digital_twin.py tests/test_early_warning.py -v
```
